# P8: Uvicorn's graceful-shutdown timeout, with a COMMIT in flight

Run on 2026-10-24. Written by: Claude Opus 5.5 (max).

This is a premise probe for §7.1 of [`../../python-production-failure-gap-analysis.md`](../../python-production-failure-gap-analysis.md), and for PY-4 in [`../../python-upstream-contribution-roadmap.md`](../../python-upstream-contribution-roadmap.md). It is not a PPCS case:

- it runs outside `harness/`, with no CTL-01 or `pg-control` gate, in its own container;
- every cell ran three times, and the repetitions agreed.

It connects two earlier results:

- **P3,** where anyio's level-triggered cancellation led SQLAlchemy to fire `after_rollback` before PostgreSQL committed;
- **[Uvicorn discussion #3232](https://github.com/Kludex/uvicorn/discussions/3232),** which shows that the graceful-shutdown timeout cancels a request once, then exits (SIGTERM) or cancels it again (SIGINT). That discussion measured a stand-in service, not PostgreSQL.

## Question

When Uvicorn's `--timeout-graceful-shutdown` expires while a request's COMMIT is in flight, what does PostgreSQL finally do? Does SQLAlchemy's `after_rollback` fire before the process exits?

## Design

**The app (`chk_app.py`)** is a plain ASGI app served by Uvicorn.

- **Lifespan:**
  - startup creates `create_async_engine(…, pool_size=1, max_overflow=0)`;
  - shutdown runs `await engine.dispose()`, as an ordinary application does.
- **The request,** a single transaction:
  1. open `AsyncSession(engine)`, then `async with session.begin():`;
  2. insert a gated row;
  3. read `pg_backend_pid()` and `pg_current_xact_id()`;
  4. leave the block, which sends COMMIT.
- **The event log.** Every SQLAlchemy ORM, Core and pool event, and every step of the request and the lifespan, is written with `os.write` to an append-only file descriptor.
  - The ORM events are `after_begin`, `after_commit`, `after_rollback` and `after_soft_rollback`.
  - A line exists only if the process reached it before exiting.

**The gate** is P3's. A `DEFERRABLE INITIALLY DEFERRED` constraint trigger runs `pg_advisory_xact_lock(777)` at COMMIT. The runner holds `pg_advisory_lock(777)` in the same database, because advisory locks are per database.

**The runner (`run_uvicorn_check.py`),** for one run:

1. creates a fresh database with the gate, and takes the lock;
2. starts Uvicorn 0.54.0 with `--timeout-graceful-shutdown 1 --lifespan on`, and sends one raw HTTP/1.1 request;
3. waits until `pg_stat_activity` shows that backend `active`, with query `COMMIT` and `wait_event = advisory`;
4. sends SIGTERM or SIGINT;
5. waits for the process to exit, then records the backend and `pg_xact_status()`;
6. releases the gate, then records the final fate and whether the row is visible;
7. extracts the backend's lines from the server log.

**Control, `TERM-in-time`:** SIGTERM, then the gate is released 0.3 s later, inside the 1 s graceful window.

## What this shows

1. **PostgreSQL committed every interrupted transaction,** 24 of 24, and it did so after the server process had exited. At exit, every backend was still waiting in COMMIT.
2. **SIGTERM: the application's cleanup never ran.**
   - No exception reached the handler.
   - Its `finally` did not run, and no ORM commit or rollback event fired.
   - The client saw its connection close without a response.
   - There was no false rollback claim, and no outcome signal of any kind.
3. **SIGINT: SQLAlchemy claimed a rollback, then PostgreSQL committed.**
   - `after_rollback` fired before exit, and so did `after_soft_rollback`; SQLAlchemy documents `after_rollback` as "after a real DBAPI rollback".
   - The handler saw `CancelledError`, and the client received HTTP 500.
   - PostgreSQL then committed.

   This is PY-4's shape, reached without anyio, on an ordinary shutdown path. It held on SQLAlchemy 2.1.5 and 2.1.6, and with both drivers.
4. **Why no cancel reached PostgreSQL** (traceback and Src; mechanism partly Judg):
   - **psycopg.** The SIGINT tracebacks in `results-*.jsonl` show its `wait()` catching the first `CancelledError` during COMMIT. It then entered `_try_cancel` → `cancel_safe()`, and was cancelled again there, by `asyncio.run`'s teardown.
   - **Under SIGTERM,** the process ended before any cancel was sent.
   - **asyncpg.** SQLAlchemy invalidated the connection (`pool.invalidate`). asyncpg sends its CancelRequest from a background task, which connection cleanup cancels (Src, `asyncpg/connection.py`, `_clean_tasks`). That CancelRequest was not observed directly.
5. **Control.** When COMMIT could finish inside the graceful window, every signal agreed with PostgreSQL: committed, `after_commit`, HTTP 200.

## Caveats

- **The gate.** It holds COMMIT past the 1 s timeout. In production that needs a COMMIT that outlasts the configured graceful timeout, for example a deferred FK check waiting on a row lock, or a synchronous-replication stall. The window is the whole timeout, not milliseconds. No frequency is claimed.
- **`--timeout-graceful-shutdown` is off by default.** Without it Uvicorn waits for requests, and this path does not arise.
- **Signals.** Kubernetes and systemd send SIGTERM. SIGINT comes from Ctrl+C, or from process managers configured to send it.
- **Scope.** One machine; plain Uvicorn, without uvloop or httptools; no web framework above the ASGI app.
- **Paths masked.** In quoted tracebacks, local paths were replaced by `<local path removed>`. Nothing else in the outputs was changed. `summary.json` is identical before and after the masking.

## The invalid run

The first SQLAlchemy 2.1.5, psycopg, SIGINT, repetition 3 used HTTP port 8800, which another local service already held.

- Uvicorn could not bind (`[Errno 48]`), the request reached that service (HTTP 404), and nothing was gated: the record says `"gated": false`.
- Its event log is kept as `output/events-sa215/psycopg-int-3.INVALID-port-8800-in-use.jsonl`.
- The cell was rerun on a port verified to be free: `output/results-sa215-rerun.jsonl`.
- `summarize.py` excludes the invalid record.

## Changes between attempts

- **The setup helper.** The runner's `q()` first passed an empty parameter tuple, so psycopg rejected the `%` in the trigger's `like 'slow%'` during setup. That attempt measured nothing. The fix, passing parameters only when there are some, preceded every recorded run.
- **A trial run.** psycopg, SIGTERM, repetition 0, on SQLAlchemy 2.1.6, ran with the current scripts before the matrix. Its result matched the matrix, and it is not part of the outputs.
