# SQLAlchemy transaction recovery, PPCS run 2026-10-19T00-49-25Z-3673a3

SQLAlchemy 2.1.5, psycopg 3.3.6, Python 3.13.11, PostgreSQL 18.6 (`postgres:18.6@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336`). Three repetitions agreed. CTL-01 and pg-control held their gates in this run for every SQLAlchemy scenario result below.

Native mode is `Session.begin()` on the engine this adapter already builds (`pool_size` 1, `max_overflow` 0, `pool_pre_ping` off). `Session.begin_nested()` is the savepoint. `TX-03` runs in that same mode: the next unit of work is a second `Session` on the same engine, and the engine is not disposed between the units. Category C is a client-side injection in this process, fired once. `ROLLBACK TO SAVEPOINT` passes `before_cursor_execute` (`DefaultDialect.do_rollback_to_savepoint` executes the clause). A top-level `ROLLBACK` does not: `DefaultDialect.do_rollback` calls `dbapi_connection.rollback()` (`sqlalchemy/engine/default.py`). The withhold for that statement is on `psycopg.Connection.rollback`, before send. Category B is the runner's `pg_terminate_backend`. A clean exit of `Session.begin()` is reported committed. An exit with the exception raised inside the block is reported rolled back. An exit with an error the block did not raise is reported failed.

`TX-01B.commit-reply-discarded` is NOT_RUN. On this server, `Session.begin()`'s commit returned with psycopg `transaction_status` `IDLE` after it had been `INTRANS`. psycopg 3.3.6 `Connection.commit` waits on `_commit_gen`, which calls `_exec_command(b"COMMIT")` and does not return until that command finishes (`psycopg/_connection_base.py`). The caller never observes a lost COMMIT reply while the driver still reports a transaction. The node-postgres reply-lost simulation is not that probe. Closing the socket after `commit()` returns is not that loss.

`TX-02.savepoint-rollback-rejected` is a different ending from Django's run and from that withheld-savepoint result. `TX-03.rollback-not-sent` and `TX-03.statement-error-rollback-not-sent` match Django's fate: unit 1 aborted, the doomed marker is absent, and unit 2 committed a transaction of its own, so both TX-03 invariants held. ## Contract beside the failure

`TX-02.savepoint-rollback-not-sent` is the counterexample already recorded for this adapter. The withheld statement raised `RuntimeError`, which is not a database error. The outer block caught it and returned. `Session.begin()` committed. PostgreSQL committed both markers. The session was idle. TX-02.2 held. The same ending is Django's, Lucid's, MikroORM's, and pg-control unsafe. pg-control correct sends `ROLLBACK` after the withheld statement and passes.

`TX-02.savepoint-rollback-rejected` is the new counterexample. PostgreSQL's `3B001` aborted the savepoint's subtransaction and left the top-level transaction in progress. That error reached the outer block as `OperationalError` and was caught. The block then returned, so `TransactionalContext.__exit__` called `commit()` (`sqlalchemy/engine/util.py`). `DefaultDialect.do_commit` calls `dbapi_connection.commit()` (`sqlalchemy/engine/default.py`). psycopg finished `COMMIT` and moved the connection from `INERROR` to `IDLE`. PostgreSQL aborted the transaction and committed nothing. The session was idle afterward, so TX-02.2 held. TX-02.1 failed because the API reported a commit of a transaction PostgreSQL aborted.

The success is the driver's. A later measurement on these same versions, outside this run, released the savepoint `Session.begin_nested()` had created and let that block send `ROLLBACK TO SAVEPOINT`. PostgreSQL answered `3B001`. `Session.begin()` and `Connection.begin()` both returned without raising. A direct `psycopg.Connection.commit()` while the connection was `INERROR` returned `None`. The `PGresult` for that `COMMIT`, read before `commit()` discarded it, was `COMMAND_OK` with command tag `ROLLBACK`. `commit()` does not expose the tag. `pg_xact_status` was `aborted`, and neither marker was visible. PostgreSQL 18.6 `EndTransactionBlock` returns false for a failed block (`TBLOCK_ABORT`), and `standard_ProcessUtility` sets that completion to `CMDTAG_ROLLBACK`.

The added contract sentence is the exit path those two results use: if `commit()` raises on the way out, `TransactionalContext.__exit__` calls `rollback()` when it can and propagates the error from that exit. On the rejected case, `commit()` did not raise.

`TX-01A` did not reach that path. The flush of the duplicate insert rolled the transaction back while the connection was `INERROR`, and the context manager closed a deactivated transaction instead of committing. The harness records the mechanism as not exercised: after the API returned, the session was idle and its last statement was `ROLLBACK`.

## Recommendation

The new counterexample justifies one upstream question. This run does not file it.

`Session.begin()` reports success because `psycopg.Connection.commit()` returns `None` after the connection was `INERROR`. On this server that completion is `COMMAND_OK` with command tag `ROLLBACK`, and PostgreSQL has aborted the transaction. The application had already seen `3B001`. The source path above is what ran. This finding does not file the driver report.

The withheld-savepoint FAIL is the ending already recorded in `results/2026-10-17T23-08-15Z-6704a7`. It does not add a question. `TX-01A` is not a counterexample: its precondition was not established. Category B aborted the transaction, and the API did not report a commit. The `TX-03` passes are the pool sending `ROLLBACK` on the connection's return after the withheld call, then a second `Session` committing its own transaction on that backend, or, when the backend had been terminated, on a new one.
