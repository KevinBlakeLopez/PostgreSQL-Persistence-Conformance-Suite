# SQLAlchemy Core transaction recovery, PPCS run 2026-10-19T12-35-51Z-64c5c5

SQLAlchemy 2.1.5 Core, psycopg 3.3.6, Python 3.13.11, PostgreSQL 18.6 (`postgres:18.6@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336`). Three repetitions agreed. CTL-01 and pg-control held their gates in this run for every SQLAlchemy Core scenario result below. No result was INCONCLUSIVE.

Native mode is `Connection.begin()` on a connection from `Engine.connect()` (`pool_size` 1, `max_overflow` 0, `pool_pre_ping` off). `Connection.begin_nested()` is the savepoint. Writes are `insert()` and are sent when `execute()` returns. There is no `Session`, flush, or identity map. `TX-03` runs in that same mode: the next unit of work is a second `Engine.connect()` and `Connection.begin()` on the same engine, and the engine is not disposed between the units. `TX-05` sets `Connection.execution_options(isolation_level=...)` before `begin()`. Category C is a client-side injection in this process, fired once. `ROLLBACK TO SAVEPOINT` passes `before_cursor_execute` (`DefaultDialect.do_rollback_to_savepoint` executes the clause). A top-level `ROLLBACK` does not: `DefaultDialect.do_rollback` calls `dbapi_connection.rollback()` (`sqlalchemy/engine/default.py`). The withhold for that statement is on `psycopg.Connection.rollback`, before send. Category B is the runner's `pg_terminate_backend`. A clean exit of `Connection.begin()` is reported committed. An exit with the exception raised inside the block is reported rolled back. An exit with an error the block did not raise is reported failed.

Every trace begins with `ROLLBACK (INTRANS)` before the case's first statement. That call is the psycopg dialect's first-connect isolation probe: `DefaultDialect.initialize` calls `get_default_isolation_level` (`default.py`), and `PGDialect_psycopg.get_isolation_level` runs `SHOW` and then `rollback()` when the connection was idle before that query (`psycopg.py`). The `SHOW` uses the DBAPI cursor, so it is absent from the cursor trace. The following `rollback()` is what the trace records. It is not the case's rollback, and it is not a category C fault.

`TX-01B.commit-reply-discarded` is NOT_RUN. On this server, `Connection.begin()`'s commit returned with psycopg `transaction_status` `IDLE` after it had been `INTRANS`, the same transition as the ORM adapter's run `2026-10-19T00-49-25Z-3673a3`. psycopg 3.3.6 `Connection._commit_gen` calls `_exec_command(b"COMMIT")` and does not read the result (`psycopg/_connection_base.py`). `_exec_command` raises when the result status is not `COMMAND_OK` or `TUPLES_OK`. The caller never observes a lost COMMIT reply while the driver still reports a transaction. The node-postgres reply-lost simulation is not that probe. Closing the socket after `commit()` returns is not that loss.

`TX-04.independent-inner` is UNSUPPORTED, not applicable by design. `Connection.begin_nested()` is a savepoint on the same transaction. Core has no propagation mode that promises an independent transaction, and `execute()` does not defer writes. MG-02 and MG-03 are UNSUPPORTED, capability absent. Core's `Engine` and `Connection` have no migration runner. Alembic is not this adapter.

## Where the failing calls go

`Connection.begin()` and `Session.begin()` both use `TransactionalContext.__exit__` (`sqlalchemy/engine/util.py`). On a clean exit, while the transaction is still active, `__exit__` calls `commit()`. If `commit()` raises, it calls `rollback()` when it can and propagates that error. `RootTransaction._do_commit` calls `Connection._commit_impl`, which calls `DefaultDialect.do_commit`, which calls `dbapi_connection.commit()` (`default.py`). `NestedTransaction._close_impl` still deactivates the savepoint when `ROLLBACK TO SAVEPOINT` raises (`base.py`).

`TX-01A` used that exit. The duplicate `INSERT` raised `IntegrityError` (`23505`). The application caught it and sent nothing else. At `before-end` the session was `idle in transaction (aborted)` and `pg_xact_status()` already reported xid 2456 aborted, so the case's precondition held. The block then returned. `commit()` was called while psycopg reported `INERROR` and returned with the connection `IDLE`. `Connection.begin()` returned without raising, so the adapter reports a commit. After that return the session was idle and its last statement was `COMMIT`. The marker is absent. TX-01A.1 failed. This adapter did not read PostgreSQL's command tag out of psycopg. `_commit_gen` discards the result of `_exec_command(b"COMMIT")`, and `_exec_command` does not raise on `COMMAND_OK`. A `COMMIT` that completes with command tag `ROLLBACK` is `COMMAND_OK`. That source path is consistent with `commit()` returning here. It is not a separate observation of the tag.

The ORM run did not reach this exit. `Session._flush` begins a nested transaction and, on failure, calls `transaction.rollback()` (`session.py`, the `except` around `flush_context.execute()`). That run's trace was `ROLLBACK` while `INERROR`, `commit()` was not called, and at `before-end` the session was already idle. The precondition failed, so TX-01A.1 was not applied. That rollback is Session flush behavior. Core `Connection.execute()` does not do it.

`TX-02.savepoint-rollback-not-sent` is the other exit. The withheld `ROLLBACK TO SAVEPOINT` raised `RuntimeError` before send. The application caught it. The savepoint object was deactivated in `_close_impl`'s `finally`. The connection stayed `INTRANS`. `Connection.begin()` then committed. PostgreSQL committed xid 2480, and both markers are visible. The session was idle, so TX-02.2 held. TX-02.1 failed because the committed transaction still contains the failed scope's write. The ORM run is this same ending: a caught non-database error, then a commit of both markers. The ORM findings already record that ending for `Session.begin()`, Django, Lucid, MikroORM, and pg-control unsafe.

`TX-02.savepoint-rollback-rejected` caught `OperationalError` `3B001` and then took the `INERROR` commit path from TX-01A. `commit()` returned. PostgreSQL aborted xid 2495, so neither marker remains. The session was idle and its last statement was `COMMIT`, so TX-02.2 held. TX-02.1 failed because the API reported a commit of a transaction PostgreSQL aborted. The ORM run is this same ending, through the same `__exit__` and `do_commit`.

`TX-02.conn-lost-before-savepoint-rollback` caught `OperationalError` `57P01` from `ROLLBACK TO SAVEPOINT`. The outer exit then raised `PendingRollbackError` from `Connection._invalid_transaction`, which the block had not raised, so the adapter reports failed. xid 2511 aborted. The session was closed. Both TX-02 invariants held. The ORM run reported `PendingRollbackError` as well.

The `TX-03` passes are the pool. After the withheld `rollback()`, `Connection.close()` returned the DBAPI connection with reset enabled, and the pool's rollback-on-return sent `ROLLBACK` (`pool/base.py`, `_reset` when `reset_on_return` is rollback). Unit 2 then began a new transaction. When the backend had been terminated, unit 2's checkout was a new pid.

`TX-04` and `TX-05` have no ORM result to set beside them. With no fault, `begin_nested()` rolled the failed scope back to the savepoint and the outer commit kept only the outer row; a released savepoint disappeared with the outer rollback. Both isolation forms ran at `serializable`, corroborated by an `SIReadLock` on `item`.

## Recommendation

This run does not file an upstream issue.

The new counterexample is `TX-01A`. It is the same commit-while-`INERROR` question the ORM findings already state for `TX-02.savepoint-rollback-rejected`, now reached without `Session._flush`. The question is whether `TransactionalContext.__exit__` should report success when `Connection.commit` returns after the DBAPI connection was `INERROR`. On this server that return meant PostgreSQL had aborted the transaction, and the session's last statement was `COMMIT`. `Session.begin()` uses that same `__exit__`. A second report for `Connection.begin()` would describe one path twice.

`TX-02.savepoint-rollback-not-sent` does not add a question. The connection was `INTRANS`, `commit()` committed, and both markers remain. That is the ending already recorded for this SQLAlchemy version's `Session.begin()`.

No SQLAlchemy issue found in this pass states the synchronous psycopg case of `commit()` returning when PostgreSQL completes `COMMIT` with command tag `ROLLBACK`. Issue 5824 is an asyncpg commit that raises. It is a different driver outcome.

Category C results are what Core does if the injected failure happens. They are not a rate.
