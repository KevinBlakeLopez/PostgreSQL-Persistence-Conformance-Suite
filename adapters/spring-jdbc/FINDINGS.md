# Spring JDBC transaction recovery, PPCS run 2026-10-18T16-08-25Z-9b025d

Spring Framework 7.0.9 (`spring-tx` 7.0.9, `spring-jdbc` 7.0.9), PostgreSQL JDBC 42.7.14, HikariCP 7.1.0 in the pooled mode, Java 21.0.12.1, PostgreSQL 18.6 (`postgres:18.6@sha256:74935e72241653ca55e0414067e6d8763aceb8a810eb51b452253ec3dcfc4336`). Three repetitions agreed. CTL-01 and pg-control held their gates in this run for every Spring scenario result below.

Native mode is `TransactionTemplate` on `DataSourceTransactionManager` over `DriverManagerDataSource`. No pool. The outer template uses the default `PROPAGATION_REQUIRED`. A nested scope is a second `TransactionTemplate` with `PROPAGATION_NESTED`. `TX-03` runs only in the pooled mode (HikariCP 7.1.0, `maximumPoolSize` 1). Between the units the connection is released through Spring's normal path. The pool is not closed, the connection is not evicted, and no validation query is issued between them. Category C is a client-side injection in this process, fired once, before pgjdbc sends. A top-level `Connection.rollback()` never becomes a `Statement`, so that call is withheld on the connection method. `ROLLBACK TO SAVEPOINT` is withheld or rewritten on `Connection.rollback(Savepoint)`. Category B is the runner's `pg_terminate_backend`. Spring's report is not the verdict.

`TX-01B.commit-reply-discarded` is NOT_RUN. On this server, `Connection.commit()` returned with transaction state `IDLE` after it had been `OPEN`. pgjdbc 42.7.14 `PgConnection.commit` calls `executeTransactionCommand(commitQuery)` and does not return until that execute returns. The driver sets `IDLE` from the server's `ReadyForQuery`. The caller never observes a lost COMMIT reply while the driver still reports a transaction in progress. Closing the socket after `commit()` returns is not that probe.

Native `TX-03` was not executed. `DriverManagerDataSource.getConnection` opens a new physical connection. `DataSourceTransactionManager.doCleanupAfterCompletion` unbinds the holder and then calls `DataSourceUtils.releaseConnection`. After the unbind, `doReleaseConnection` closes the connection. A probe on this server released a connection whose autocommit was false: the connection was closed and its backend was gone. The next `TransactionTemplate` used a different backend (966 then 967; the first was absent after `execute` returned). That is `not-applicable-by-design` for handing a transactionally active connection to later work. The pooled rows are the mode that can check a connection out again.

None of the TX-02 rows is TypeORM's ending. TypeORM's TX-02 failure leaves the session idle in transaction and keeps neither marker. The withhold case committed both markers and the session was closed. The rewrite case kept neither marker, and the session was closed, not idle in transaction. The connection-loss case kept neither marker and the session was closed, and the API did not report a commit.

## Contract beside the failures

`TX-02.savepoint-rollback-not-sent` is the counterexample that matches Django and SQLAlchemy. The withheld statement raised `SQLException`. The nested `TransactionTemplate.execute` left with `TransactionSystemException`, not the application error. The outer callback returned normally, and the outer template called `commit()`. PostgreSQL committed both markers. The session was closed afterward. TX-02.2 held.

The 7.0.9 reference says `PROPAGATION_NESTED` uses a single physical transaction with multiple savepoints, and that a partial rollback lets the outer transaction continue. `DataSourceTransactionManager` implements that with a JDBC savepoint. A thrown `rollbackToSavepoint` does not mark the outer transaction rollback-only. The outer callback's normal return then commits.

`TX-02.savepoint-rollback-rejected` is a different ending from Django. PostgreSQL's `3B001` aborted the transaction before the outer template returned. The outer callback still returned normally, so the template reported a commit. PostgreSQL aborted xid 1217 and kept neither marker. TX-02.1 failed. TX-02.2 held.

`TX-01A.caught-error-then-commit` is also a different ending from Django. The callback caught `DuplicateKeyException` (`23505`), sent nothing else, and returned. `execute` returned normally, so the report is committed. PostgreSQL had already aborted xid 1178, and the marker is absent. TX-01A.1 failed. Django rolled that transaction back.

`TX-03.rollback-not-sent` is the other new counterexample. The withheld `ROLLBACK` left the session idle in transaction. The template reported failure. Cleanup then ran. At `after-unit1` the same session was idle and its last statement was `COMMIT`, xid 1248 was committed, and the doomed marker was visible. pgjdbc 42.7.14 `PgConnection.setAutoCommit(true)` calls `commit()` when a transaction is open, and `doCleanupAfterCompletion` restores autocommit after `rollback()` has thrown. HikariCP then checked that backend out again. Unit 2 committed xid 1249 on pid 12600. TX-03.1 failed because unit 1 was committed. TX-03.2 held.

The statement-error case is the contrast. The unique violation had already aborted unit 1 before the withheld `ROLLBACK`. The later `COMMIT` from restoring autocommit did not commit that transaction: xid 1263 stayed aborted and the doomed marker was absent. The same backend was reused, and unit 2 committed a transaction of its own. Both TX-03 invariants held.

Category B did not report a commit. Where the runner terminated the backend, the transaction aborted.

## Recommendation

Keep the cases in PPCS. Do not file an issue.

Two of the failures justify an upstream question, as a question rather than a defect report.

One question is whether a thrown savepoint rollback, including an exception that is not a data-access error, should mark the outer transaction rollback-only before a normal return commits. The withhold case committed both markers. The rewrite case reported a commit after PostgreSQL had aborted the transaction. Django's `3B001` path rolled the outer transaction back; this template did not.

The other question is whether `DataSourceTransactionManager` should restore autocommit after `rollback()` has thrown. Restoring it made pgjdbc send `COMMIT`. The transaction whose rollback had been withheld was committed, and the pool reused the backend. The statement-error case shows the same cleanup on a transaction PostgreSQL had already aborted: that transaction stayed aborted.

`TX-01A` is the same commit question in a smaller shape. The callback returned normally, `Connection.commit()` did not throw, and PostgreSQL had aborted the transaction. The session had closed by report time, so the last statement was not observed.

Category C does not say how often the fault occurs, and it is not a network failure. Category B aborted the transaction, and the template did not report a commit.
