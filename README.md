# PostgreSQL Persistence Conformance Suite (PPCS)

PPCS is a reproducible laboratory for transaction correctness in persistence frameworks, run against a real PostgreSQL server. It drives a framework through its own APIs and injects controlled failures. It then checks, through PostgreSQL itself, whether what the framework reported matches what the server did.

It answers questions like these:

- When a framework reports that a transaction committed, did PostgreSQL commit it?
- When the commit outcome is unknowable to the client, does the framework still assert one?
- After a nested scope's savepoint rollback fails, can its abandoned writes be committed anyway?
- After a rollback fails, can the pool hand the connection, still holding the failed transaction, to unrelated work?
- Does nested transactional work land in the boundary the framework's propagation API promises?
- When application code asks for an isolation level, does the transaction run at that level?

## Why

A framework's report of a transaction outcome is a claim. A framework's own test suite usually checks that claim with the framework's own reads, often against mocks. PPCS checks it independently:

- **Transaction identity:** each transaction's ID is read inside it, with `pg_current_xact_id()`, and checked against that session in `pg_stat_activity`.
- **Fate:** a separate connection asks PostgreSQL for that transaction's fate, with `pg_xact_status()`, when the API returns and again after the framework is gone. It also asks which writes are visible, and which transaction inserted each one.
- **Fault labels:** every fault is labelled by what it is: an error PostgreSQL generated, a server-side termination, or a client-side injection. Its effect is confirmed on the server.
- **Controls:** a result counts only if, in the same run, the framework's own observation controls passed, the suite's positive and negative controls behaved as expected, and three repetitions agreed.

## What PPCS does not claim

- **A FAIL is not a defect report.** It is a reproducible counterexample to a stated PPCS invariant, under recorded versions, settings and fault category. Each FAIL quotes the framework's contract for the API it called, so that readers can judge it against the framework's own promises.
- **Injected faults show recovery paths, not frequency.** Category C and D faults are injected in the client. They show what a framework does *if* that failure happens, not how often it happens in production.
- **PPCS is not a ranking, a benchmark, an ORM, or a replacement for a framework's own tests.**

## A caught unique violation

On PostgreSQL, a caught unique violation (`23505`) aborts the transaction. `COMMIT` then completes with command tag `ROLLBACK` and does not raise. Several frameworks still report success. MikroORM 7.2.5 does. A follow-up on 7.2.6-dev.19 rejects that commit; npm `latest` was still 7.2.5. The recorded runs, the versions, and the issues already filed are in [`docs/caught-unique-violation.md`](docs/caught-unique-violation.md).

## Quick start

Requirements: Docker (with Compose), Node.js 24, pnpm 12. JDK 21 for the Hibernate, Spring JDBC, Spring transaction, jOOQ, and plain JDBC adapters. PHP 8.5.6 and Composer for the Laravel and PDO adapters. .NET SDK 10.0.402 for the EF Core adapter and the Npgsql control. Go 1.27.3 for the pgx control, the database/sql control, and the GORM adapter. `pnpm run setup` does not install PHP, the .NET SDK, or Go. When `go` is already on `PATH`, setup downloads the Go module.

```sh
pnpm run setup     # frozen-lockfile install of the harness and the JavaScript adapters
pnpm run pg:up     # disposable PostgreSQL 18.6 on 127.0.0.1:55435 (pinned image digest, tmpfs, random password)
pnpm run ppcs      # every case on every adapter; writes results/<run id>/summary.md and JSON evidence
pnpm run pg:down   # removes the container
```

- **Filters:** `node harness/run.mjs --adapter=lucid --case=TX-01A --mode=native`. The controls each result depends on always run with it.
- **Repetitions:** every case runs three times by default (`--repeat=<n>`).
- **Regression check:** `--expect=<earlier run.json>` exits 1 if any classification changed. It refuses (exit 2) an earlier run made with a different harness or catalog.
- **Self-tests:** `pnpm run test` for the classification rules, with no database; `pnpm run test:methodology` for the controls through the real runner.

A full run of the JavaScript adapters takes about six minutes. Django, SQLAlchemy, and Tortoise each need the virtualenv in their adapter README. Hibernate, Spring JDBC, Spring transaction management, jOOQ, and the plain JDBC control need JDK 21 and `mvn -B package` in `adapters/hibernate`, `adapters/spring-jdbc`, `adapters/spring-tx`, `adapters/jooq`, and `adapters/jdbc-control`. The EF Core adapter and the Npgsql control need .NET SDK 10.0.402 and `dotnet build -c Release` in `adapters/efcore` and `adapters/npgsql-control`. The Go adapters need Go 1.27.3. `adapters/go` is the module, and each adapter's `./run` script is `go run`. `pnpm run setup` does not install those. The runner refuses any server that is not the disposable instance, or whose settings differ from the profile the cases assume. It never touches another database (`docs/methodology.md`).

## What is implemented

**Specifications** (`specifications/`, described in `docs/specifications.md`): 9 families, 24 cases. Lucid and `pg-control` execute MG-02 and MG-03. Django implements the two TX-04 savepoint cases through nested `transaction.atomic()`, both TX-05 forms through the connection `OPTIONS` `isolation_level`, and MG-02 and MG-03 through `MigrationExecutor`. It declares `TX-04.independent-inner` not applicable by design. The SQLAlchemy ORM adapter implements the two TX-04 savepoint cases through `Session.begin_nested()`, and both TX-05 forms through `Session(execution_options={"isolation_level": ...})`. It declares `TX-04.independent-inner` not applicable by design and the migration cases capability-absent. Spring JDBC does not implement TX-04 or TX-05, and declares the migration cases capability-absent. SQLAlchemy Core implements TX-04 and TX-05 and declares the migration cases unsupported. Tortoise implements the two TX-04 savepoint cases. It declares `TX-04.independent-inner` and both TX-05 cases unsupported, and the migration cases capability-absent. Drizzle implements the transaction cases through `db.transaction()`, including the savepoint TX-04 cases and managed TX-05, and MG-02 through `migrate()`. It declares `TX-04.independent-inner` not applicable by design, `TX-05.explicit-serializable` capability-absent, and MG-03 capability-absent. Prisma implements the transaction cases through `prisma.$transaction()`, including nested `tx.$transaction()` savepoints and managed TX-05, and MG-02 through `prisma migrate deploy`. It declares `TX-04.independent-inner` not applicable by design, `TX-05.explicit-serializable` capability-absent, and MG-03 capability-absent. The plain JDBC control implements the savepoint TX-04 cases and TX-05, and declares `TX-04.independent-inner` and the migration cases unsupported. Spring transaction management implements TX-04, including `PROPAGATION_REQUIRES_NEW`, and both TX-05 forms in the programmatic mode. The declarative mode does not run the explicit TX-05 form. It declares the migration cases unsupported. Hibernate ORM implements CTL-01, TX-01A, TX-01B connection loss, and pooled TX-03 through `Session.beginTransaction`. It declares TX-02, TX-04, TX-05, and the migration cases unsupported. `TX-01B.commit-reply-discarded` is not run. jOOQ Open Source Edition 3.21.9 implements the transaction cases through `DSLContext.transaction`, and a second mode executes the same SQL while the application calls `Connection.commit`. It declares `TX-04.independent-inner` not applicable by design and the migration cases capability-absent. `TX-05.explicit-serializable` runs only in the JDBC-owned mode. `TX-01B.commit-reply-discarded` is not run. Active Record implements the transaction cases through `ActiveRecord::Base.transaction`, with `requires_new: true` for a savepoint, and MG-02 and MG-03 through `MigrationContext`. It declares `TX-04.independent-inner` not applicable by design and `TX-05.explicit-serializable` capability-absent. The ruby-pg control implements the same cases as `pg-control` and is not a matrix column. EF Core implements the transaction cases through `Database.BeginTransactionAsync` and `CommitAsync`, with `CreateSavepointAsync` for a nested scope, and MG-02 and MG-03 through `Database.MigrateAsync`. The native TX-01A violation is `SaveChangesAsync`. The `execute-sql` mode uses `Database.ExecuteSqlAsync` for that violation. It declares `TX-04.independent-inner` not applicable by design and `TX-05.managed-serializable` capability-absent. The Npgsql control is not a matrix column. `TX-01B.commit-reply-unseen` is category E: the runner's protocol proxy drops the reply to `COMMIT` before the driver reads it. Django, both SQLAlchemy adapters, Tortoise, Spring JDBC, Spring transaction management, Hibernate, jOOQ, Laravel, and the plain JDBC, PDO, and `pg-control` controls implement it. Lucid, MikroORM, TypeORM, Drizzle, Prisma, Active Record, and EF Core do not. `TX-01B.commit-reply-discarded` stays the category D simulation.

Explicit TX-05 is the JDBC-owned mode and is also `serializable`. The migration cases are capability-absent. `org.jooq.Migrations` is in the open-source jar and is not this adapter. `TX-01B.commit-reply-discarded` is NOT_RUN. pgjdbc does not return from `commit()` until the driver state is `IDLE`. No issue was filed.
- **Active Record.** The column is `ActiveRecord::Base.transaction` and `create!`. Three framework FAILs: TX-01A, with the COMMIT-answered-ROLLBACK mechanism exercised, and both client-side TX-02 cases. The outer `transaction` returns after the inner savepoint rollback is withheld or rejected; the original backend is gone and a different backend sends `COMMIT`. TX-03 passes on a new transaction id. Both implemented TX-04 cases pass. `TX-04.independent-inner` is not applicable by design. Managed TX-05 runs at `serializable`. `TX-05.explicit-serializable` is capability-absent. MG-02 and MG-03 pass except `MG-02.idle-session-timeout`, which is INCONCLUSIVE. `TX-01B.commit-reply-discarded` reports `failed` after a client-side discarded reply; TX-01B.2 is not exercised. The ruby-pg control is not a column.
- **EF Core.** The column is native `Database.BeginTransactionAsync` and `CommitAsync`. Marker inserts use `ExecuteSqlAsync` so the row `xmin` is the top-level transaction. Native TX-01A is INCONCLUSIVE: `SaveChangesAsync` of the duplicate rolls back to an automatic savepoint, the transaction stays open, and the earlier marker commits. The failed entity stays `Added`. `execute-sql` fails TX-01A: `CommitAsync` returns, the commit interceptor runs, and PostgreSQL aborted the transaction. The backend is already gone at `after-end`. Both client-side TX-02 cases fail when the application catches the savepoint error and calls `CommitAsync`. A withheld rollback commits the inner write. A rejected rollback reports a commit of a transaction PostgreSQL aborted. Pooled TX-03 passes on a new transaction id of the same backend. Both implemented TX-04 cases pass. `TX-04.independent-inner` is not applicable by design. Explicit TX-05 runs at `serializable`. Managed TX-05 is capability-absent. `Database.MigrateAsync` passes MG-02 and MG-03. `TX-01B.commit-reply-discarded` is NOT_RUN. The Npgsql control is not a column. `correct` reports `rolled_back` after `SELECT 1` fails with `25P02`, and the last statement is still `COMMIT`. `unsafe` reports `committed` when `CommitAsync` returns.
- **GORM.** The column is `DB.Transaction`. Explicit `Begin` / `Commit` agreed on the cases both modes ran, except the TX-03 report value noted above. One framework FAIL: `TX-02.savepoint-rollback-not-sent`. The outer commit returns nil and both markers are visible. `RollbackTo().Error` was nil while pgx recorded the failed statement. TX-01A passes with the mechanism exercised: `ErrTxCommitRollback`, command tag `ROLLBACK`. The rejected-savepoint case passes for the same reason. TX-03 passes on a new backend. `TX-04.independent-inner` is not applicable by design. Both TX-05 forms run at `serializable`. The migration cases are capability-absent. The pgx and database/sql controls are not columns.
- **Laravel.** The column is Eloquent writes through `Connection::transaction()`. Explicit `beginTransaction()` / `commit()` / `rollBack()` agreed on every case both modes ran. Eight framework FAILs: TX-01A, with the COMMIT-answered-ROLLBACK mechanism exercised, all three TX-02 cases, and all three TX-03 cases. `PDO::commit()` returned true on TX-01A and the marker was absent. pdo_pgsql does not expose the command tag. On the withheld savepoint rollback, Laravel reported success without calling `PDO::commit()`, and the session was still in a transaction. The persistent mode also fails the three TX-03 cases. Both TX-04 savepoint cases pass. `TX-04.independent-inner` is not applicable by design. Both TX-05 forms run at `serializable`. `TX-05.explicit-serializable` is the explicit mode. `TX-01B.commit-reply-discarded` and the migration cases are NOT_RUN.
- **Qualifiers:**
  - **"Mechanism not exercised":** Lucid's `pre-commit-probe` passes TX-01A by failing before COMMIT. Django's native TX-01A passes the same way in substance: it rolls back inside the block, and COMMIT is not the statement that ends the transaction. Neither is evidence that the framework reads a ROLLBACK command tag on COMMIT.
  - **"TX-01B.2 not exercised":** the framework adapters observe no channel through which a framework could claim a rollback, so TX-01B.2 was not tested for them.
- **Report time:** where a transaction was still open when the API returned, each FAIL says so, and says whether teardown or later work decided its fate. In TypeORM's TX-02 cases, for example, the transaction was open at report time and rolled back at teardown. SQLAlchemy's rejected-savepoint FAIL is not that ending. The session was idle when the API returned.
- **Controls:** the positive control passes every case it implements. The negative control fails the 17 cases it is built to fail, so the runner detects a known-bad implementation. That includes unsafe connection reuse, which the observer sees server-side: the next unit of work runs inside the failed transaction's own ID. It also includes a write lost with a failed nested scope, a requested isolation level dropped by a plain `BEGIN`, a migration applied twice, and a reversal that leaves history and the database disagreeing. Every control expectation held in each of these runs, so no result was gated.
- **Detail:** each FAIL in `reports/examples/*/summary.md` gives what the API reported, what PostgreSQL did at report time and at the end, what the application could know, the violated invariant, the framework's contract, and a reproduction command.

## Classifications

| Classification | Meaning |
| --- | --- |
| PASS | Every exercised invariant of the case held, with complete and consistent observations. A qualifier marks an invariant or a mechanism that was not exercised. |
| FAIL | An invariant was violated. The result names it, with the observations, the conditions and the contract basis. |
| UNSUPPORTED | The adapter's manifest declares that the framework's supported API does not expose what the case tests, or that the hazard cannot arise by design. Never a failure. |
| INCONCLUSIVE | The run did not establish a conclusion. Causes include a timeout, a protocol error, a missing or unconfirmed observation, a precondition that did not hold, observations that contradict each other, disagreeing repetitions, or controls that did not hold in the run. Never a PASS. |
| NOT_RUN | The case was not executed: not implemented by the adapter, or filtered out. |
