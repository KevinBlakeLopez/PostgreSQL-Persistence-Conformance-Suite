Framework contract: Hibernate ORM 7.4.13.Final Transaction (org.hibernate.Transaction) is a resource-local transaction begun with Session.beginTransaction and ended with Transaction.commit or Transaction.rollback. The interface javadoc says there is at most one uncommitted transaction for a Session, and that after a rollback the persistence context must be discarded because Hibernate does not restore entity state. PostgreSQLDialect.causesRollback returns true, so JdbcCoordinatorImpl.afterFailedStatementExecution marks the JDBC transaction rollback-only when a statement throws SQLException. That call does not send ROLLBACK. JdbcResourceLocalTransactionCoordinatorImpl.commitRollbackOnly, when the transaction is MARKED_ROLLBACK, calls rollback and returns. AbstractLogicalConnectionImplementor.begin calls Connection.setAutoCommit(false) unless the provider already disabled autocommit. rollback calls Connection.rollback and then afterCompletion. If Connection.rollback throws, status becomes FAILED_ROLLBACK and afterCompletion is not called. afterCompletion calls Connection.setAutoCommit(true) only when autocommit was on at begin, then releases the connection when the handling mode is not ON_CLOSE. Session.inTransaction delegates to TransactionManagement.manageTransaction, which calls Transaction.rollback when the action throws and the transaction is still active. A returning Transaction.commit is reported as committed. A returning Transaction.rollback, followed by the application error leaving the boundary, is reported as rolled_back. An exception leaving the boundary is reported as failed. It is not a claim that PostgreSQL rolled back. TX-01A catches the statement error inside the work and then calls Transaction.commit.
